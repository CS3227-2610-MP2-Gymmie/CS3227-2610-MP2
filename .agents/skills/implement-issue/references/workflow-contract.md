# Issue Implementation Workflow Contract

This contract accompanies the `implement-issue` skill and may evolve in response to observed failures. Ordinary issue records support practical review. Controlled comparisons require the evaluator to preserve equivalent starting inputs and record the workflow actually used; this evaluation responsibility does not make identity metadata or evaluation infrastructure mandatory for routine implementation.

Use these statuses for work that is not fully complete: **blocked** means an unavailable dependency, environment, or external state prevents progress; **awaiting-decision** means a material choice needs the user's input; **incomplete** means work or evidence remains without such a blocker. Mark work **completed** only when the required outcome has observable evidence.

## Requirements

| ID | Applies when | Expected behavior | Observable evidence |
| --- | --- | --- | --- |
| IW-01 | Every implementation task. | Understand the requested outcome and inspect enough of the applicable instructions, repository conventions, documentation, source, and tests to establish scope. Resolve routine uncertainty from evidence. Do not invent requirements; surface material ambiguity or conflict and pause only dependent work for a decision. | The task scope and acceptance criteria are understood, or unresolved items and their impact are reported. |
| IW-02 | Before changing files. | Establish the baseline by inspecting the current branch and revision, working-tree status, and relevant existing changes. Preserve unrelated work. A baseline does not require a commit, a clean working tree, or a full test run before each edit. | The branch/revision and status are known; relevant existing changes remain intact and can be distinguished from task changes. |
| IW-03 | Work has acceptance criteria or a non-trivial change. | Plan proportionally by mapping each criterion to an intended change and observable verification. Keep the plan lightweight; revise it when evidence changes scope, assumptions, dependencies, or expected behavior. | A concise plan or working map connects criteria, changes, and checks; material changes to that map are reflected. |
| IW-04 | Implementation or associated docs/tests are in scope. | Make focused changes within the authorized scope. Add or update tests appropriate to the behavior and update affected documentation when repository conventions or the change require it. If required documentation is missing, add the smallest suitable entry or scaffold within scope. Preserve test intent; do not weaken or bypass tests to get a pass. | The diff is scoped; relevant tests and documentation reflect the change or any omission is explained. |
| IW-05 | Every implementation task. | Review the final diff against the request, plan, and relevant invariants. Repair findings and re-review affected changes when findings exist; revisit the plan when evidence changes the intended scope or approach. Make each retry evidence-driven. After two materially different unsuccessful approaches to the same obstacle, stop speculative retries and report what decision, input, or capability is needed. | The review is performed and findings are resolved or clearly statused; affected work is rechecked, or the stopping point and needed intervention are stated. |
| IW-06 | Every implementation task reaches verification. | Verify the final relevant code state with actual repository tooling and checks suited to the acceptance criteria. Include suitable interface checks when affected behavior warrants them; do not require GUI checks for every behavior change. If relevant edits occur after a check, rerun it when needed before claiming the criterion passed. If evidence is unavailable, report the limitation and do not claim a pass. | Checks or observations, actual results, and the code state checked are associated with each criterion; any relevant later edits or unavailable evidence are identified. |
| IW-07 | Every implementation task reaches delivery. | Report outcomes and remaining work honestly. Distinguish completed, blocked, awaiting-decision, and incomplete criteria; separate observed evidence from assumptions and identify material limitations. | Delivery summary states criterion status, evidence, assumptions/limitations, and what remains without unsupported success claims. |
| IW-08 | Git or external actions are considered. | Prepare or use a task branch when appropriate under repository conventions, preserving existing work. Stage and commit only when authorized by the user and applicable instructions; authorization in the task request is sufficient, so do not ask again. Push requires separate authorization. Perform external actions only within the user's explicit authorization and applicable instructions. | Branch changes preserve prior work; staging/commit and external actions match authorization, and their results are reported. |

## Applying the loop

Follow **Understand → Plan → Implement and Test → Review → Fix as needed → Verify → Deliver → Commit when authorized**. Scale investigation, planning, testing, and reporting to risk and complexity. A stage can be brief when its purpose is already satisfied; the sequence does not require separate documents or approval checkpoints.

Choose checks from the current repository's tools and conventions rather than assuming a language, build system, test runner, CI setup, or interface. Run verification after fixes against the final relevant code state. If a necessary check cannot run, try a suitable in-scope alternative when available and report what remains unverified.

Apply applicable repository and environment instructions alongside the user's request. Configuration, scripts, CI, permissions, and sandboxing enforce only what they demonstrably enforce; written conventions remain instructions unless backed by such mechanisms. Do not infer precedence from this contract. If applicable directions conflict materially, preserve work and seek the smallest needed clarification.
